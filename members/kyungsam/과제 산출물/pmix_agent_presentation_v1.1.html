Introduction

P-Mix 수익성 Simulation Agent

자연어 질의로 P-Mix 수익성을 분석하고, 변수 조정에 따른 수익성 변화를 즉시 정확하게 계산하며 인사이트를 제공하는 도메인 특화 Agent입니다.

정확한 Simulation

변수를 조정하면 기존 시스템과 동일한 로직으로 수익성 변화를 즉시 계산합니다.

Ch 1. 과제 배경

제품이 늘고 시장이 흔들릴수록, 판단은 더 빨라져야 했습니다

P-Mix 타당성 점검과 매출·기회비용 검토 요구가 늘면서, P-Mix 변화가 수익성에 미치는 영향을 신속히 검토하고 공유할 분석 체계가 필요했습니다.
1

유례없는 포트폴리오 확대

AI 시대에 맞춘 고객 맞춤형 대응으로 제품 포트폴리오가 유례없이 확대되고, 시장 환경도 급변하고 있습니다.

검토해야 할 P-Mix 경우의 수 자체가 이전과 비교할 수 없이 늘었습니다.
2

담당자 경험에 얹힌 판단

Validation Rule과 분석 Point가 암묵지 형태로 존재. 담당자가 바뀌면 지식이 함께 사라질 위험.

시스템화 이후에도 다량의 Table 지표를 직접 탐색해야 했습니다.
3

Manual Report 이상의 해석

Manual화된 Report 이상의 특이사항과 인사이트 추출은 암묵지 영역으로, 담당자 역량에 크게 좌우됩니다.

수치가 바뀌면 Report를 처음부터 다시 작성해야 하는 부담도 남아 있었습니다.
데이터 수집(Step 1)은 ’25년 시스템 구축으로 이미 자동화됐지만, 해석과 판단은 여전히 사람의 몫으로 남아 있었습니다.
Ch 1. 요구사항

Agent에 요구된 세 가지

이 세 가지가 이후 모든 설계 판단의 기준이 되었습니다.
1

시스템과 숫자가 같아야 한다

AI가 기존 G-SCM의 계산 로직을 그대로 사용해, 화면에서 조회한 값과 동일한 결과를 보여줄 것.

수익성 숫자는 보고에 그대로 쓰입니다. LLM이 값을 “생성”하면 그 순간 쓸 수 없는 도구가 됩니다.
2

자연어를 파라미터로

사용자 질의를 파라미터화하여, 원하는 수익성 지표 조회와 Simulation을 동적으로 수행할 것.

“고정 질문 몇 개에 답하는 챗봇”이 아니라, 조회 조건을 자유롭게 조합할 수 있어야 합니다.
3

숫자 너머의 해석

집계·Simulation 결과를 LLM이 분석해 의미 있는 특이사항과 추가 인사이트를 제공할 것.

가장 어려웠던 요구사항입니다. 이유는 Lesson Learned에서 말씀드리겠습니다.
Ch 2. 구현

Agent 주요 기능 레이어

사용자 질의는 Orchestrator를 거쳐 기능 Layer로 라우팅되고, 각 Layer는 자신의 역할만 수행합니다.
1
Orchestrator
사용자의 자연어 요청을 정규화하고, 적절한 기능 Layer로 라우팅하며 flow를 제어함
주요 기능 : 요청 해석 및 구조화, Flow 라우팅, 필수 파라미터 체크, 결과 값 출력
2
Validation
수익성 Plan Ver Data의 이상치를 식별하고 누락치 조정 결과를 해석함
주요 기능 : 누락치 요약, 누락치 입력 프로시저 Call
3
Analysis
수익성 Plan Ver Data의 다각적 분석을 수행하기 위해 Data를 연산하고 요약함
주요 기능 : 월별 트렌드 분석, Mix 분석, Ver간 비교 분석, 원인 분석
4
Simulation
사용자가 수익성 Data의 변수를 조정하여 기준 Plan Ver 대비 수익성 변화를 산출함
주요 기능 : QTY(Mix) Simulation, ASP Simulation, 수율 Simulation
5
Case 생성
담당자가 설정한 제약 조건 하에서 최적의 P-Mix Case를 탐색해 제안함 · Phase 2
주요 기능 : 제약 조건 정의, 후보 Case 생성 및 평가, 최적안 추천
6
Data Retrieval
각 기능 Layer가 필요로 하는 데이터를 표준화된 방식으로 조회해 전달함
주요 기능 : Ontology 참조, 수익성 Data IF, 프로시저 Call

Ch 2. 구현 특징  (1/2)

Agent 구현 특징 — 판단은 어떻게 만들어지는가

추론은 Agent Layer가 하고, 집계 및 계산은 AI가 개입되지 않는 순수 MCP Layer가 수행합니다.
1
Semantic Layer — LLM의 판단 기준을 코드 밖으로
사용자 질의 분석, 파라미터 맵핑, 호출 도구 선택 등 LLM의 모든 판단에 Semantic Layer를 개입시킵니다.
구현 방법  Orchestrator와 Sub Agent의 각 prompt에 Semantic Layer를 스크립트 파일(.d2 확장자)로 주입
2
ReAct Pattern — Reasoning + Act
사용자 질의가 들어오면 지정된 횟수(10회)로 Loop를 돌며 답변이 완성됐는지 체크하고, LLM에 Binding된 Tool을 호출합니다.
구현 방법  GaiA의 LangGraph 버전이 ReAct 패턴(Deep Agent, create agent)을 지원하지 않아, 유사한 동작을 Code Level에서 직접 구현
3
기능별 Tool Binding — 동적 도구 선택
LLM은 Prompt 및 Binding된 도구의 설명을 참조하여 상황에 맞게 동적으로 Tool을 선택합니다.
구현 방법  최상위 Orchestrator에 Binding된 도구 목록(Tool 15개, Sub Agent 2개)으로 구성. 정상 사용이 완료된 Tool은 1회 Loop 내 재호출되지 않음
Ch 2. 구현 특징  (2/2)

Agent 구현 특징 — 계산과 문맥은 어떻게 지키는가

Agent와 MCP가 주고받는 표준 객체 인자를 먼저 합의하고, 계산은 전적으로 MCP Layer에 맡깁니다.
4
집계 처리 엔진 — AI가 개입하지 않는 계산
GaiA(Agent Layer)와 집계 처리 엔진(MCP Layer) 간 사전에 합의된 Parameter Payload(Dimension, Measure)를 이용하여 Wafer 장당, DIE당, EQ, 제품, 연간 등 다양한 수익성 지표를 산출합니다.
구현 방법  기존 장당 수익성 화면의 조회 조건·Dataset·SQL을 FastAPI의 MCP 서버 Python 소스로 Conversion하여 통합 구축
5
Parameter Mapping — Agent와 MCP의 공용어
Analysis·Simulation의 세부 동작에 필요한 Parameter를 집계축(Dimension)과 계산값(Measure) 두 가지로 구조화하여, Agent와 MCP 통신을 위한 표준 객체 인자로 활용합니다.
구현 방법  제품 속성은 Dimension, 수익성 지표는 Measure로 두고 G-SCM 실제 Table 및 UI 변수와 정확히 같은 이름을 Default로 설정 · 항목별 상세 Description을 Semantic Layer와 Tool마다 기입 · Aggregation과 Simulation의 API 파라미터로 JSON 객체 사용
6
Context Retention — 대화가 이어지게 만들기
이전 대화의 문맥을 저장한 후 응답 생성에 참고하는 Multi Turn 대화가 가능합니다.
구현 방법  Multi Turn 질의가 들어오면 이전 대화 기록을 JSON 형태로 불러와 프롬프트에 주입. GaiA Framework가 Default 외 확장 State를 저장하지 않아 별도 Tmp 파일로 저장

OLAP 성격의 대용량 기간계 시스템에 AI를 붙이면서 얻은, 다음 과제에 그대로 쓸 수 있는 것들입니다.
1
Context 최적화가 곧 품질
Semantic Layer · 상세 프롬프트 · 채팅 히스토리 · 전체 Dataset을 다 넣으면 조회 시간과 Context 크기 제약에 부딪힙니다.
2
추론과 연산은 반드시 분리
판단은 LLM·Agent가, 비즈니스 로직 계산은 MCP(API)가. 이 경계를 지켰기 때문에 “시스템과 같은 숫자”가 성립했습니다.
3
단순 수치 해석은 인사이트가 아니다
최대·최소·증가 추이 수준의 러프한 해석은 현업에게 의미 있게 다가가지 않습니다. 도메인 맥락이 결합되어야 합니다.
4
구조화 경험 자체가 자산
Agent에 주입하기 위해 데이터와 비즈니스 로직을 구조화한 경험은 다른 도메인에도 그대로 적용됩니다.
5
속도와 완성도는 Context가 가른다
같은 모델, 같은 Tool이라도 Context 관리 수준에 따라 답변 품질 차이가 매우 큽니다.
6
OLAP 시스템에서의 AI 도입 방식
대용량 집계 시스템에 AI를 어떤 형태로 붙일지 고민하고 실제로 검증해 볼 수 있었습니다.

결국 한 문장으로

AI에게 판단을 맡기고 계산은 맡기지 않는 것, 그리고 업무 지식을 프롬프트가 아니라 관리 가능한 계층으로 분리하는 것. 이 두 가지가 기간계 시스템 위에서 Agent를 성립시킨 조건이었습니다.
