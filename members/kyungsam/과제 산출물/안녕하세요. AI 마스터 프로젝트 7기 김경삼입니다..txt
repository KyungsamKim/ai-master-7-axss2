안녕하세요. AI 마스터 프로젝트 7기 김경삼입니다.
제가 만든 것은 하이닉스SCM 대화형 수요 데이터 분석 Agent입니다.
Agent는 G-SCM 수요 영역의 조회 결과를 받아서, 차트와 해석과 보고서를 만들어주는 읽기 전용 분석 레이어의 기능을 제공합니다.

2P
먼저 문제 정의입니다.
하이닉스 반도체 공급망 관리 시스템인 G-SCM에는 약 1500개의 수많은 조회 화면이 있습니다.
그리고 그 90% 이상이 표와 그리드를 정해진대로 보여주고 끝납니다.
화면이 주는건 표 한장이고, 그게 무슨 뜻인지 해석하는건 담당자의 몫입니다.
표 데이터를 엑셀로 내려받아 피벗을 돌리고, 차트를 만들거나 보고서 형태로 가공해서 사용합니다.
이 작업은 최소 30분 걸리며 담당자의 숙련도에 따라 최종 결과물이 정해집니다.

고객사는 기존 SCM의 조회 및 분석 업무에 AI 기능을 얹어 달라는 요청을 했고,
차년도 차세대 착수에 앞서 선행 PoC로 이 과제를 기획했습니다.

기획 초기에 갈림길이 하나 있었습니다. 화면마다 전용 에이전트를 만들 것인가, 공통 레이어를 만들것인가.
화면마다 만들면 공수가 화면 수에 비례하고 총 1500개 화면이 있기에 그 방식은 불가능하다는 결론을 내렸습니다.
그래서 조회 결과에 온톨로지와 시장 자료를 범용적으로 활용하는 공통 레이어를 선택했고,
이 선택이 프로젝트 전체를 결정했습니다.

다음으로 핵심 기능입니다.
에이전트의 가장 핵심 로직은 두가지입니다.
첫번째는 SQL 조회 결과를 10개의 Chart 생성 Rule과 5개의 인사이트 해석 Rule을 지키도록 검사하고
모든 Rule을 지킬때까지 생성과 개선을 반복하는 것입니다.
두번째는 LLM은 절대로 숫자를 만들어 내지 않는 것입니다.
이것이 가장 중요한 Constitution(헌법)이며 로직의 중심입니다. LLM을 금지하여 할루시네이션 없는 문장과 Facts들을 먼저 만들어내고, 그 Facts를 기준으로 차트와 인사이트를 만듭니다. ||

에이전트는 LangGraph 기반으로 18개 노드와 2개의 병렬 분기, 5개의 피드백 루프로 구성되며
자세한건 아키텍처에서 이어서 설명하겠습니다.

핵심 성과는 숫자 세 개로 말씀드리겠습니다.
첫째 30분을 21초로 줄였습니다.
기존에 엑셀 피벗하고 차트 정리하는데 최소 30분이 들었는데, Agent가 이 작업을 21초만에 해줍니다.

두번째 화면별 개발 공수는 거의 0입니다.
올해 상반기 7개 조회 화면 대상으로 Agent 개발을 이미 해봤고 총 5명 3개월, 15MM 소요됐습니다.
제가 만든 에이전트는 화면에 대한 설명만 yaml로 등록하면 끝나고, 어떤것도 화면별로 개발하지 않습니다. 오직 필요한건 공용 레이어입니다.

세번째 할루시네이션과 잘못된 숫자가 없습니다.
숫자는 LLM이 금지된 Compute Facts 노드에서 만들고 15개의 검사 Rule이 있기에 모든 숫자는 추적가능한 데이터입니다.

한 문장으로 줄이면 표 한장으로 끝나던 조회에서, 차트와 인사이트 해석까지 조회의 영역으로 확장됩니다. 모든 차트와 인사이트는 추적 가능한 구조기 때문에 나온 숫자를 그대로 보고와 업무에 사용할 수 있습니다.

3P
다음으로 기술 아키텍처입니다.
왼쪽이 전체 에이전트 상세 구조입니다. 위에서 아래로 따라가겠습니다.
입력은 항상 두 가지입니다. 기존 조회 화면이 이미 갖고 있는 검증된 SQL의 실행 결과와 화면 YAML 및
의미 계층으로 구성된 온톨로지 입니다. 텍스트-투-SQL의 정확도 문제를 아예 방지한게 특징입니다.

이번 마스터 과제에서는 입력을 위해 streamlit으로 UI UX를 만들었지만 실제 차세대 환경은
리액트와 스프링 부트 기반 시스템에서 에이전트 레이어를 호출하는 방식으로 구현할 예정입니다.
라이브러리 선정시 리액트와 스프링부트 호환성까지 고려했습니다.

1번부터 7번까지는 전부 규칙 기반 코드들 입니다. 7번까지 왔을 때 분석 계획을 만들 근거가 없으면 7번에서 멈추고 사용자에게 다시 되묻습니다. 

8번 분석 계획에서 LLM이 처음 들어옵니다. 8번 노드에서 유일하게 ReAct 패턴이 쓰입니다.
추론 - 실행 - 관찰 패턴에 가장 적합하다고 판단했습니다. 다만 보통의 ReAct패턴과 다르게
추론과 검증은 정해진 규격의 Rule에 의해서만 LLM이 판단하고 새로운 가정은 만들지 않습니다.

9번 Comupte Facts 사실 확정 노드, 여기는 LLM이 개입하지 않으며 모든 숫자를 만드는 가장 중요한 노드입니다. 데이터 원본과 소계를 분리하고 가중평균을 계산하는 등 여러 기법으로 이후 사용할 의미 있는 숫자 데이터를 만들어냅니다. 화면에 뜨는 모든 수치는 이 곳에서 SQL 결과 기반으로 만들어지기에 틀리지 않습니다.
이 제약이 없다면, LLM은 어떻게든 차트와 문장을 만들고 할루시네이션 가능성이 있기에 9번 노드가 가장 핵심으로 동작합니다.

숫자를 만든 다음은 두 갈래로 갈라져 동시에 돕니다. 10~12번 노드는 차트 영역입니다. 
코드 기반으로 차트의 패턴과 모양을 결정합니다.  차트 생성 전 10개의 항목으로 차트 스펙을 검사하고 하나라도 미달되면 되돌아갑니다. 
13번 노드는 회사 외부의 마켓 인텔리전스를 기반으로 데이터를 해석하는 기능입니다.
데이터셋과 온톨로지 두개의 인풋과 회사 외부 시장자료를 RAG 기반으로 비교하여 
관련 문단을 찾고 대조표를 만듭니다.

병렬로 각각 차트와 시장 자료 세그먼트를 만들면 14번 노드에서 기다렸다가 결과를 합칩니다. 
15번에서 대조표를 기반으로 실제 분석 인사이트를 생성하고 15-b번에서는 차트와 인사이트간
서로를 근거로 연결하는 작업을 합니다. 
16번 노드에선 통합된 인사이트가 아닌 차트 한개에 대한 수치 분석도 추가적으로 만듭니다.
18번에서 최종 결과를 조립하고 이 때 조립에 실패한 부분이 있어도 최소한 표는 나갑니다. 
부가적으로 보시는 바와 같이 5개의 피드백 루프가 쓰였습니다.

다음은 기술 선택 이유와 고려사항입니다.
첫번째로 프레임워크와 도구로 LangGraph와 MCP를 기본 골격으로 잡았습니다.
LangChain이 아닌 LangGraph를 채택한 중요한 이유는 두가지 입니다.
첫번째는 9번 Compute Facts 노드에서 산출된 결과 state를 각 차트와 시장 자료 노드로 병렬 처리하여
응답 속도와 성능 최적화를 하기 위함입니다.
더 중요한 두번째는 차트 10개 해석 5개 규칙 ReAct 패턴 등 조건을 만족하지 못하면 특정 노드에 State를 가지고
되돌아가는 기능이 필수였기 때문입니다. 
최종 Output의 두 축인 차트와 인사이트 모두 한번에 결과가 나오는 것이 아닌 여러번의 Loop를 통해
모든 규칙을 통과하도록 되어 있습니다.

MCP는 제공자와 소비자로 분류할 수 있으며 주로 차트 영역에 사용합니다. 차트를 그릴 때는 
소비자로 Vega Lite MCP를 호출하여 차트 렌더링에 씁니다.
제공자로는 에이전트의 분석 기능들 11개를 MCP 도구로 뺐습니다. MCP로 구현한 이유는
MCP Tool 형태로 만들어서 다른 에이전트도 호출할 수 있게 하기 위함입니다.

두번째로 시장 자료 기반 해석은 BM25 Sparse RAG를 활용했습니다. 별도로 임베딩이나 Vector DB를 쓰지 않았습니다. 
Sparse RAG를 선택한 이유는 첫번째 시장 자료는 계속 업데이트 되어 Fine-tuning으로는 못 따라갑니다.
둘째 실제 고객사에서 진행중인 MI 프로젝트와 A2A로 인터페이스 할것이 자명하기에 오버 프로그래밍하지 않기 위해서입니다.
문서 10건 - 179개 청킹 (문단 최대 900자)

마지막 세번째는 온톨로지와 결정론적 계산입니다. 
조회 속성이 60개에 Row수는 제품 Level을 상세하게 하면 1000개가 넘어가는 쿼리가 많습니다.
모든 데이터를 프롬프트에 넣으면 프롬프트가 오염되어 컨텍스트가 너무 낭비됩니다.
그렇기에 온톨로지와 맵핑하여 실제 필요한 데이터만을 Pandas로 추출 및 가공해서 사용합니다.
필요 데이터만 결정론적으로 가공해서 실제 데이터를 보호하는 장점과 토큰 및 응답속도를 줄이는 장점을 얻습니다.

(문서 10건을 179조각으로 쪼개고 가장 가까운 3개만 인용하는데, 중요한 건 관련이 낮으면 아예 인용하지 않는다는 겁니다. 
억지로 붙인 배경은 없느니만 못하기 때문입니다)

4P
가장 어려웠던 것은 성능도 연동도 아니었습니다. 차트와 해석을 어떻게 만들 것인가에 대한 설계였고, 여기서 처음에 크게 실패했습니다.
처음에는 조회 결과를 LLM에게 넘기고 차트와 인사이트를 만들어 달라고 단순하게 요청했습니다.
결과는 나왔습니다. 그런데 같은 SQL을 다시 넣어도 매번 다른 차트와 다른 해석이 중구난방으로 나와 전혀 쓸 수 없었습니다.
원인은 모델이 아니라 제 접근이었습니다. 무엇이 좋은 차트이고 좋은 해석인지, 그 기준을 제가 정하지 않고 모델에게 맡겼던 겁니다.
여기서 배운 것이 이 프로젝트의 설계 원칙이 됐습니다. LLM에게 판단을 맡기기 전에, 판단 기준부터 만들어야 한다.
그래서 차트 가시성과 데이터 신뢰성 두 가지를 핵심 목표로 다시 잡았습니다.

먼저 차트의 가시성을 확보하기 위해 실제 G-SCM UI와 보고 자료에 쓰이는 차트를 8개 유형으로
분류했고 축 범위, 단위, 배색, 표시 개수 등을 디테일하게 나눴습니다.
조회 결과 속성의 종류, 데이터 Row수를 종합하여 부합하는 형태의 차트로 렌더링하여 화면별로
차트를 그리지 않아도 G-SCM에서 직접 그린것과 유사한 차트들을 뽑을 수 있었습니다.

두번째는 데이터 신뢰성입니다. 해석과 인사이트는 9번 노드의 숫자로 단순히 최대, 최소, 변곡점, 추이를 뽑아내는 정도의 인사이트가 아닙니다. 병렬로 수행한 차트, 시장 대조표의 문단을 합쳐서 5개 항목으로 검사를 해서 만듭니다.
그렇기에 도메인 지식 혹은 배경 지식이 있는 전문가가 만든 인사이트처럼 나옵니다. 시장 자료가 업데이트될 때마다
뷰가 바뀌므로 편향된 고정적인 인사이트도 아니게 됩니다.

여기서 쓴 알고리즘 및 기법은 간단히 말씀드리겠습니다. 계획 수립은 ReAct 패턴을 사용했으며 해석의 자기 교정은 Reflexion을 썼는데 전형적인 Reflexion을 그대로 쓰지는 않았습니다.
반성의 주체를 모델에서 코드로 바꿨습니다. 문장으로 나온 수치와 Facts를 대조해서 없는 숫자면 제외하도록
Self- Correction 합니다.

결과와 성과를 다시 세개 숫자로 말씀드리겠습니다. 
먼저 15개 항목입니다. 
위에서 말한 상세 규칙 즉, 차트 10개, 해석 5개를 통과해야 하며 이 규칙들을 만족하기 위해 내부적으로 많은 Loop를
돌며 점차 완성됩니다.
두번째로 8+6입니다. 
가시성 측면에서 조회 SQL 하나가 최대 8개의 차트 종류와 6개의 뷰로 다양하게 변환됩니다.
마지막으로 인사이트의 문장들에 나온 모든 숫자는 각주 형태로 추적 가능합니다. 실시간으로 근거를 볼 수 있기에
사용자는 해당 Output을 그대로 보고자료로 활용 가능해집니다.




# 노드명 하는 일 유형
1 ingest SQL 결과 수집 (결과 없으면 → 18) 규칙
2 route_intent 새 분석 / 다시 분석 / 다시 그리기 판정 규칙
3 resolve_semantic_layer 화면 YAML에서 컬럼 뜻·단위 해석 규칙
4 enrich_context 코드값 풀이 등 맥락 보강 규칙
5 profile 데이터 모양 파악 (행·열·소계·기간) 규칙
6 classify_screen_type 화면 유형 판정 (빈 결과 / 상세 목록 / 분석) 규칙
7 clarify 근거 없으면 멈추고 되묻기 (interrupt) 규칙
8 plan_analysis 분석 계획 — 조합이 많을 때만 LLM (ReAct) LLM
9 compute_facts 사실 확정 · 가중평균 · 소계 분리 LLM 금지
10 present 차트 패턴 선택 · 중립 차트 스펙 생성 규칙
11 verify_chart 차트 검사 10항목 검사
12 render_chart_mcp Vega-Lite MCP로 렌더 규칙
13 market_context 시장 자료 서브그래프 (안에 search_market → align_market → suggest_questions) 규칙
14 merge_branches 합류 — 두 갈래가 다 끝나야 열림 (defer) 합류
15 generate_insight 해석 작성 + 검사 5항목 → 불합격 시 재작성 (Reflexion) LLM
